# Yakker 1.7.0 — Schedule padding and recording recovery

Protect the beginning and ending of a scheduled show, retain more audio when a
stream stalls, and recover interrupted recordings with clearer capture times.
The Focus player and saved-show playback carry forward from 1.6.

## Schedule padding

- **Start early** and **End late** add up to ten minutes on either side of a
  scheduled show. New schedules suggest 30 seconds early and one minute late;
  existing schedules keep their timing with padding off until you edit it.
- The editor's automatic preview and upcoming list show the effective capture
  window, including seconds. Expanded recording details separate the show's
  scheduled interval, intended capture window and recorded process times.
- Padding follows the saved timezone and daylight-saving occurrence, including
  windows that cross midnight. It counts toward existing storage and simultaneous
  recording limits, so adjacent shows can overlap.
- Editing or disabling a future schedule leaves an active capture and its linked
  remainders on their original station, label and padded window.

## Recording endings and recovery

- Source reading and Opus writing now run independently over a bounded in-memory
  float PCM pipe. If an HLS reader stalls, the writer can drain received audio and
  finish its final Ogg page. Smaller output pages also improve retained audio
  after abrupt termination. No temporary PCM recording is written to disk.
- Capture start/end timestamps exclude later writer drain and file inspection.
  An early stream exit stays partial even when finalization finishes after the
  scheduled deadline. Captures whose deadline has already passed are rejected.
- After a forced controller exit, recovery preserves a known end time and leaves
  an unknown one unavailable. It no longer reports the restart time as though
  recording continued during the outage.
- Recoverable segments stay playable and separate. Linked remainders preserve
  their original identity and capture window. Retry backoff and the three-attempt
  limit survive controller restarts; explicit Stop and expired windows do not
  start another capture.
- Reader stalls and writer failures have distinct partial-recording explanations.
  A finalized file does not prove that every desired broadcast sample arrived.

## Timing and audio quality

Recordings remain **mono Opus at 24 kbit/s VBR**. Audio duration measures retained
audio, while scheduling follows the computer clock. Broadcasters can deliver
buffered audio or HLS segments in bursts, making a file longer than its capture
window. Provider latency and network setup also affect broadcast boundaries.

Recovery cannot reconstruct missing source audio. Controlled tests observed
roughly two-to-four-second gaps around ordinary drops/restarts. A connection
that stopped delivering data recovered in about 17 seconds, including the
existing 15-second input timeout. Forced termination can still lose buffered
ending audio. There is no wake timer or separate recording service; the machine
must remain awake with the widget loaded.

Developer tools now provide time-coded boundary audits, live-station schedule and
resume checks, controlled connection/restart recovery tests, and matched-source
24/48 kbit/s listening comparisons. These run with isolated data. Broadcaster
connections require explicit station selection; the recovery audit is loopback
only. The production bitrate is unchanged.

## Upgrade and rollback

Finish active recordings and stop foreground playback before installing and
restarting the shell. Install the QML and controller together from the same
checkout or extracted archive.

Before upgrading, back up `~/.local/share/yakker/recordings.json`, or
`$XDG_DATA_HOME/yakker/recordings.json` if configured, while recordings are idle.
Version 1.7 reads older recording indexes and preserves existing schedule timing.
Once padded schedules or new recordings are saved, v1.6.0 cannot read the added
index fields. Keep the metadata backup with the previous plugin for rollback;
the installer's plugin backup contains code, not recording metadata. Recordings
created after the backup will not appear in a restored older index.

From a source checkout:

```sh
make build
./yakker install
omarchy restart shell
```

Compiled archives already contain both executables. Run `./yakker install` from
the extracted `yakker/` directory, then restart the shell. Existing audio files,
station preferences, widget placement and recording storage stay in place.

## Release files and validation

- `yakker-1.7.0-linux-amd64.tar.gz`
- `yakker-1.7.0-linux-arm64.tar.gz`
- `yakker-1.7.0-source.tar.gz`
- Individual `.sha256` files and `yakker-1.7.0-SHA256SUMS`.

Validation includes formatting, vet, module verification, race-enabled tests,
real-mpv integration, native recording UI and keyboard checks, compact layouts,
three live padded schedules, and eight controlled recovery scenarios. The live
checks covered strict decoding, reference-delivery boundaries, pause/seek,
saved-position resume across controller restart, and playback through EOF.
The controlled cases included disconnects, a stalled connection, retry exhaustion,
graceful/forced restart, initial HTTP failures, user Stop and expired windows.

Native gallery screenshots use illustrative data and varied stations. Playback
checks use null audio and do not establish subjective audio quality or exact
broadcaster program-clock alignment. Physical suspend/resume and power loss
remain manual acceptance checks. Both Linux archives include build information
and dependency license notices; ARM64 is cross-built and archive-checked, with
playback on physical ARM64 hardware still unverified.
