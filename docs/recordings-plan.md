# Scheduled recordings: discussion draft

This scopes todo #3 for discussion before implementation. Capture compatibility still needs a feasibility test. The first use case is **WBZ-FM, Fridays 14:00–14:20**, on the computer's local time, while the user can listen to another station. Recordings are separate from the existing temporary listening buffer.

## Current starting point

Yakker is a Quattro QML bar widget. `RadioService.qml` launches one shell-owned `yakker-controller`; `internal/radio` supervises one mpv player, and the controller shuts down when the last widget is removed. `Panel.qml` currently provides the player and settings. The controller merges the bundled `stations.json` with the user's custom-station file and publishes the catalogue to QML; default terminal sessions use a merged snapshot. Widget preferences live in Quattro's shell configuration. `yakker install` copies a managed plugin into the user's Omarchy plugin directory. None of these currently supplies a durable scheduler or recording library.

## Proposed experience

Add a **Recordings** button to the native popup and a navigable sub-screen with a Back control. Show two sections: **Schedules** (next occurrence, enabled state, edit, enable/disable, delete) and **Recordings** (newest first, station and optional title, scheduled and actual local times, duration, status and size). The editor selects a station, optional label, weekdays, start and end time, and timezone, with a clear next occurrence preview. Support end times on the following day explicitly; reject zero duration and set a sensible maximum such as 12 hours. The example previews Friday 14:00–14:20 in the selected zone. Do not silently use a broadcaster's timezone.

Recording rows offer Play, Stop and Delete, plus an error/partial explanation when applicable. Playing a file uses the existing foreground playback controls and replaces foreground live listening after an explicit Play; returning to a station remains available. Seeking within a file should use file duration rather than the live DVR timeline. Recording jobs continue independently of foreground stop, station changes, seeking, popup closure, or shell restart. Preserve keyboard navigation, focus, accessible names and readable empty/error states. A service-unavailable message must distinguish unavailable scheduling from a merely empty library.

## Schedule and time semantics

Store a weekly rule as weekdays, start and end wall times, an explicit IANA timezone, enabled flag, stable ID and revision. Default a new rule to the machine's current timezone **at creation**, displaying its name; later machine timezone changes do not silently move it. Users can edit the zone. Compute occurrences using timezone rules for each date, not a fixed UTC offset. Save each occurrence's resolved UTC start/end, local date and zone as well as a stable `(schedule ID, local start date)` identity to prevent duplicate starts after a restart or clock adjustment.

Proposed DST policy: a nonexistent spring-forward start is missed with an explanation; for an ambiguous fall-back start use the first occurrence only. Resolve the end using the first matching instant strictly after the start; if nonexistent or unable to yield a valid positive interval, mark that occurrence missed. Display the next resolved local time and offset. Test these policies explicitly and revisit them with the user. Allow edits to affect future occurrences only; a running job retains its original snapshot and end. Disable/delete prevents future starts and does not interrupt a running job; the row offers a separate Stop recording action. Deleting a schedule leaves its existing files and history.

## Background architecture

Recommend an opt-in **systemd user service**, separate from the shell-owned controller, running a small Go scheduler/recorder. A shell-owned helper alone cannot meet the shell restart/disabled-widget requirement. The service owns schedules, occurrence state and child capture processes; the UI connects over a private per-user Unix socket in `$XDG_RUNTIME_DIR` using a versioned, bounded request/response protocol. Read current persisted state on connect and send change notifications; reject stale revisions on edits. Serialize mutations in the service, restrict socket and storage permissions, and never expose a network listener. Multiple widget instances are clients, not independent schedulers.

Install/enable the service only as an explicit recordings setup step, with a visible service status and actionable failure. A user service depends on the user manager being running: do not promise recording while logged out unless lingering is separately enabled by the user. The installer/release must ship a stable executable and user unit, handle upgrades/restarts, and never point a persistent unit at a transient staging path. On normal service stop, terminate and reap each child and persist partial results. Restart recovery reconciles the persisted occurrence and files before starting future work. Avoid adopting unrelated processes or spawning duplicates. Do not modify global system configuration.

Each active occurrence gets an independent, silent capture process and network connection, including overlapping schedules for the same station. Set an explicit initial concurrency limit (suggest 3); an occurrence that cannot start because the limit is reached is marked missed with the reason, never silently queued past its start. Foreground mpv has its own process, socket and lifecycle. This costs network bandwidth and disk space per capture, but avoids playback controls affecting recordings.

## Capture and file format

Propose **ffmpeg stream copy to Matroska (`.mka`)**, one process per occurrence, selecting the first audio stream and copying its codec without re-encoding. This avoids a fixed lossy re-encode and makes a single container choice practical across common codecs; compatibility with actual station streams and interrupted outputs still needs testing. Use explicit input/output options, no shell interpolation, no overwrite, a bounded connection/stop policy, and a temporary filename with an explicitly selected muxer. Stop at the resolved wall-clock end, signal graceful finalization and wait; escalate after a bounded timeout and label incomplete output partial. A successful process exit alone does not establish that useful audio was captured: validate nonempty audio and duration with a suitable probe before marking complete. Do not claim exact broadcast boundary accuracy: connection startup, network stalls and source delay affect content.

This adds an explicit `ffmpeg` runtime dependency, checked before enabling and surfaced in the UI; do not install it automatically. mpv is already a Yakker dependency and could instead use `--stream-record`, but its installed manual says that option overwrites the destination, infers format from its extension, and seeking or switching can break recording. A dedicated mpv could avoid foreground seeking, but capture, output validation and failure semantics must still be proven. The installed ffmpeg manual documents `-c copy` and notes that stream copy can fail when the target container lacks required information. Current machine inspection found mpv 0.41.0 and ffmpeg 9.0.2; neither presence nor codec compatibility is guaranteed on another installation. See the installed `man mpv` (`--stream-record`) and `man ffmpeg` (Streamcopy), and upstream [mpv manual](https://mpv.io/manual/stable/#options-stream-record) and [FFmpeg documentation](https://ffmpeg.org/ffmpeg.html#Streamcopy). No live station capture has been tested for this proposal. Prototype representative bundled and custom streams before committing to the dependency and container; report unsupported sources as failures rather than silently transcoding.

## Persistence, recovery and limits

Use a private application data directory under `$XDG_DATA_HOME` (default `~/.local/share/yakker`) for the library and durable index, outside the replaceable plugin installation. A schedule stores station ID plus a snapshot of display name and stream URL; each occurrence snapshots those values again when planned/started. That lets a recording's history survive catalogue changes or custom-station deletion. Use the shared merged catalogue from todo #4 for station selection; an edited station should update a schedule only by an explicit user action or a clearly stated refresh policy. Avoid leaking stream URLs in UI/logs, since custom URLs may contain credentials.

Use stable generated IDs rather than station names for paths. Persist schedules, occurrence identity, planned/actual timestamps, status, error, byte count and relative file path with atomic same-directory write/rename and appropriate durability; serialize writers and use versioned schema. Persist a starting record before launching a child. Write media to a unique `.partial` file on the same filesystem; finalize and validate it, rename to its final name, then atomically publish complete status. On recovery reconcile the index and both names: never mark an unvalidated file complete; retain recoverable partials with an explanation, handle missing files explicitly, and prevent orphaned files from becoming invisible. Deletion updates index and file with recoverable ordering, validates paths stay within the library, and reports failures; no automatic deletion of recordings.

Expose a configurable storage cap and a minimum free-space reserve, with visible usage and conservative defaults to agree on. Check before and during capture, stop with a partial/error if a limit or write failure occurs, and account for simultaneous jobs. Limits must not imply a hard reservation against other applications. No cleanup of older files without a separate explicit user action.

On restart or resume, reconcile the occurrence ledger against current time. If an entire interval passed while unavailable, mark it missed; if still in progress, start once for the remaining interval and mark it partial with the actual start. A capture interrupted by suspend, service restart, lost stream or disk failure remains partial and reports the reason; do not append incompatible fragments or claim a continuous complete file. If resumed within the interval, a new linked segment may capture the remainder, with the gap visible. No wake timer or wake from sleep is proposed. Detect wall-clock jumps and recompute deadlines; duplicate suppression must survive backward jumps. Bound retry/backoff within the interval and show gaps instead of claiming uninterrupted capture.

Disabling the widget should leave an enabled recording service and its jobs running; make this behavior visible. Removing the plugin must offer an explicit choice to stop/disable the service while preserving schedules and recordings, or to retain the service with a stable executable; it must never leave an enabled unit pointing to deleted plugin files. A separate, clearly confirmed library deletion removes user data. Define upgrade, disable and uninstall commands and tests before shipping, without changing today's removal behavior invisibly.

## Bounded milestones and acceptance

1. **Capture feasibility:** use local deterministic HTTP audio fixtures and representative station formats to compare ffmpeg `.mka` capture and playback, graceful stop, interrupted output and audio probing. Record compatibility and dependency results; no scheduler or live-source claims from fixture tests alone.
2. **Durable engine:** implement weekly occurrence calculation, revisioned persistence, service lifecycle and independent capture. Tests cover weekday/overnight and DST gaps/folds, clock jumps, duplicate suppression, simultaneous jobs, foreground independence, failures, storage limits, restart/suspend reconciliation and atomic recovery. Exercise real processes against local streams as well as fakes.
3. **Native UI and lifecycle:** add schedule editor, library playback/deletion and service diagnostics; test keyboard/focus, stale edits, file versus live controls, popup/shell restart and overlapping captures in a real desktop session. Verify install, upgrade, disable and removal preserve user data and stop or retain the service as explicitly chosen. Document manual suspend/login tests and their results separately from automated tests.

## Decisions for discussion before implementation

1. Is an opt-in background user service acceptable, including the login/lingering limitation and continued operation when the widget is disabled?
2. Is adding ffmpeg acceptable if the feasibility test supports `.mka` stream copy? Would a common transcoded format be preferred despite extra CPU and quality loss?
3. Are the timezone/DST, no-wakeup, missed/partial and running-job edit policies above appropriate?
4. What concurrency, storage cap and free-space reserve should be defaults, and should a custom library location be supported in the first version?
5. Should deleting a schedule leave a currently running recording active, and should removing the plugin stop the background service by default while preserving files?
