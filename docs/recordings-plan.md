# Scheduled recordings: discussion draft

This scopes todo #3 for discussion before implementation. Capture compatibility still needs a feasibility test. The first use case is **WBZ-FM, Fridays 14:00–14:20**, on the computer's local time, while the user can listen to another station. Recordings are separate from the existing temporary listening buffer.

## Decisions from discussion

- Record only while the machine is awake and the plugin has an active bar widget. Popup closure and stopped foreground listening do not disable recording; removing/disabling the widget and a full shell restart do. No independent user service, logged-out recording or wake timers are needed.
- Playback outside Yakker is secondary. Recommend mono Opus at a target 32 kbit/s with variable bitrate in an Ogg `.opus` file, subject to a real talk-radio listening/seek test. This is a recommendation for the next feasibility step, not an approved recording implementation.
- Put the recording folder and total storage cap in Settings. Suggested defaults remain 5 GiB and `$XDG_DATA_HOME/yakker/recordings` (normally `~/.local/share/yakker/recordings`), with a 1 GiB free-space reserve. The user has chosen configurability; these default numbers and cleanup policy are proposals.

## Current starting point

Yakker is a Quattro QML bar widget. `RadioService.qml` launches one shell-owned `yakker-controller`; `internal/radio` supervises one mpv player, and the controller shuts down when the last widget is removed. `Panel.qml` currently provides the player and settings. The controller merges the bundled `stations.json` with the user's custom-station file and publishes the catalogue to QML; default terminal sessions use a merged snapshot. Widget preferences live in Quattro's shell configuration. `yakker install` copies a managed plugin into the user's Omarchy plugin directory. None of these currently supplies a durable scheduler or recording library.

## Proposed experience

Add a **Recordings** button to the native popup and a navigable sub-screen with a Back control. Show two sections: **Schedules** (next occurrence, enabled state, edit, enable/disable, delete) and **Recordings** (newest first, station and optional title, scheduled and actual local times, duration, status and size). The editor selects a station, optional label, weekdays, start and end time, and timezone, with a clear next occurrence preview. Support end times on the following day explicitly; reject zero duration and set a sensible maximum such as 12 hours. The example previews Friday 14:00–14:20 in the selected zone. Do not silently use a broadcaster's timezone.

Recording rows offer Play, Stop and Delete, plus an error/partial explanation when applicable. Playing a file uses the existing foreground playback controls and replaces foreground live listening after an explicit Play; returning to a station remains available. Seeking within a file should use file duration rather than the live DVR timeline. Recording jobs continue independently of foreground stop, station changes, seeking and popup closure. Disabling/removing the last widget or fully restarting the shell interrupts active recordings and preserves recoverable output as partial. Preserve keyboard navigation, focus, accessible names and readable empty/error states. A recorder-unavailable message must distinguish a disconnected helper from a merely empty library.

## Schedule and time semantics

Store a weekly rule as weekdays, start and end wall times, an explicit IANA timezone, enabled flag, stable ID and revision. Default a new rule to the machine's current timezone **at creation**, displaying its name; later machine timezone changes do not silently move it. Users can edit the zone. Compute occurrences using timezone rules for each date, not a fixed UTC offset. Save each occurrence's resolved UTC start/end, local date and zone as well as a stable `(schedule ID, local start date)` identity to prevent duplicate starts after a restart or clock adjustment.

Proposed DST policy: a nonexistent spring-forward start is missed with an explanation; for an ambiguous fall-back start use the first occurrence only. Resolve the end using the first matching instant strictly after the start; if nonexistent or unable to yield a valid positive interval, mark that occurrence missed. Display the next resolved local time and offset. Test these policies explicitly and revisit them with the user. Allow edits to affect future occurrences only; a running job retains its original snapshot and end. Disable/delete prevents future starts and does not interrupt a running job; the row offers a separate Stop recording action. Deleting a schedule leaves its existing files and history.

## Plugin-owned runtime

Extend the existing shared shell-owned Go helper to own schedules, occurrence state and independent capture processes. The helper already has a single-owner lock, JSON-lines communication with QML and cleanup on shell/widget shutdown. Extend that bounded protocol for recording state and revisioned mutations; the UI reads persisted state on startup and rejects stale edits. Multiple monitor widgets share one recorder. A live bar widget is required, but audio playback and an open popup are not.

Each active occurrence gets an independent silent FFmpeg process and network connection, including overlapping schedules for the same station. Suggest an initial configurable concurrency limit of 3. An occurrence that cannot start because the limit is reached is marked missed with the reason, rather than queued beyond its start. Foreground mpv retains its own process/socket. Stopping or switching foreground playback must not clean up capture workers; final helper shutdown must terminate and reap all of them and persist partial results. Retain the short widget-recreation grace period so an ordinary component refresh does not immediately interrupt recording.

No systemd unit, persistent background daemon, lingering configuration or new network listener is needed. A full shell restart or disabling/removing the last widget ends the recording runtime. Schedules and the library survive on disk and are reconciled when the plugin next becomes available. Suspension can interrupt intake; do not inhibit sleep or wake the machine to fulfill a schedule. Treat interrupted output as partial and surface any gap.

## Capture and file format

Recommend **FFmpeg encoding directly to mono Opus at a target 32 kbit/s VBR**, stored in an Ogg `.opus` file. The `.mka` and Ogg formats are containers; codec and bitrate determine most of the size. Copying the original stream into `.mka` retains the broadcaster's bitrate. Re-encoding to Opus gives a smaller, more predictable storage budget for speech at the cost of encoding CPU and an additional lossy generation. Use one profile initially; a 24 kbit/s compact profile can be considered after listening tests rather than adding settings prematurely. Ogg Opus is specified in [RFC 7845](https://datatracker.ietf.org/doc/html/rfc7845); [RFC 6716](https://datatracker.ietf.org/doc/html/rfc6716#section-2.1.1) gives a 28–40 kbit/s range for fullband speech. FFmpeg documents the encoder's [bitrate and VBR controls](https://ffmpeg.org/ffmpeg-codecs.html#libopus).

Illustrative audio-payload estimates, using decimal MB and excluding container overhead; VBR output varies with content:

| Profile | 20 minutes | One hour |
| --- | ---: | ---: |
| Opus at 24 kbit/s | 3.6 MB | 10.8 MB |
| Opus at 32 kbit/s (recommended starting point) | 4.8 MB | 14.4 MB |
| Original stream copied at 128 kbit/s (example source rate) | 19.2 MB | 57.6 MB |

The existing mpv playback engine decoded and started at a seek offset in locally generated mono Opus samples in both Ogg `.opus` and Matroska `.mka`. That verifies basic local format support, not broadcaster capture, sustained encoding cost, interrupted-file recovery, speech quality or Yakker's unimplemented recording playback UI. Before choosing the final profile, compare 24/32 kbit/s with an actual talk-radio sample, test playback/seek of finalized and interrupted files, and measure CPU with overlapping encoders. The existing player can supply the audio engine; recording playback still needs a file mode with duration-based seek controls.

This adds an explicit FFmpeg runtime dependency with libopus encoding support, checked before recording is enabled. Capture and encode directly to a unique temporary file in the chosen library folder; avoid a full-size intermediate recording. Select the first audio stream, downmix to mono, use argument arrays without a shell, and explicitly choose the output muxer for the temporary extension. Apply bounded connection/retry/stop policies. At the scheduled wall-clock end, request graceful finalization, wait and escalate only after a timeout. Probe nonempty audio and duration before marking complete; retain interrupted output as partial. Connection startup, source delay and network gaps affect which broadcast content falls within the requested time window.

## Persistence, recovery and limits

Keep schedules, settings and the durable library index under `$XDG_DATA_HOME/yakker` (normally `~/.local/share/yakker`), outside the replaceable plugin installation. Settings exposes the recording folder, defaulting to its `recordings/` subdirectory, and total storage cap, initially proposed as 5 GiB. A schedule stores station ID plus a snapshot of display name and stream URL; each occurrence snapshots those values again when planned/started. That lets a recording's history survive catalogue changes or custom-station deletion. Use the shared merged catalogue from todo #4 for station selection; an edited station should update a schedule only by an explicit user action or a clearly stated refresh policy. Avoid leaking stream URLs in UI/logs, since custom URLs may contain credentials.

Use stable generated IDs rather than station names for paths. Persist schedules, occurrence identity, planned/actual timestamps, status, error, byte count and relative file path with atomic same-directory write/rename and appropriate durability; serialize writers and use versioned schema. Store each recording's folder and relative filename so a later folder change does not lose older entries. Persist a starting record before launching a child. Write media to a unique `.partial` file on the same filesystem; finalize and validate it, rename to its final name, then atomically publish complete status. On recovery reconcile the index and both names: never mark an unvalidated file complete; retain recoverable partials with an explanation, handle missing files explicitly, and prevent orphaned files from becoming invisible. Deletion updates index and file with recoverable ordering, validates paths stay within the library, and reports failures; no automatic deletion of recordings.

Expose storage usage beside the folder and cap controls. Propose a 1 GiB minimum free-space reserve in addition to the user-chosen library cap. Check before and during capture, stop with a partial/error if a limit or write failure occurs, and account for simultaneous jobs. A folder change applies to future recordings; existing files remain listed in their original locations, with no silent move. Count managed files in older locations toward the library cap. If a chosen folder is unavailable or unwritable, show the error and do not silently switch locations. Lowering the cap below current usage preserves files and blocks new captures until space is freed or the cap is raised. Propose manual deletion when full, with automatic deletion disabled by default. Limits do not reserve space against other applications.

On restart or resume, reconcile the occurrence ledger against current time. If an entire interval passed while unavailable, mark it missed; if still in progress, start once for the remaining interval and mark it partial with the actual start. A capture interrupted by suspend, helper/shell restart, lost stream or disk failure remains partial and reports the reason; do not append incompatible fragments or claim a continuous complete file. If resumed within the interval, a new linked segment may capture the remainder, with the gap visible. No wake timer or wake from sleep is proposed. Detect wall-clock jumps and recompute deadlines; duplicate suppression must survive backward jumps. Bound retry/backoff within the interval and show gaps instead of claiming uninterrupted capture.

Disabling/removing the last widget stops active captures and the scheduler. Closing the popup or pressing foreground Stop does not. Removing the plugin preserves recording files, settings and schedules; deleting library data is a separate explicit action. Installation and upgrades ship the extended helper and preserve the external library. No separately enabled recorder remains after the plugin is disabled or removed.

## Bounded milestones and acceptance

1. **Capture feasibility:** local deterministic HTTP fixtures plus representative talk-radio content; compare 24/32 kbit/s Opus, original audio, sizes, encoder CPU, simultaneous encoders, graceful stop, interrupted output, probing, mpv playback and seeking. Select the final profile from evidence. The local format smoke test above is an initial check only.
2. **Plugin-owned engine:** implement weekly occurrences, revisioned persistence and independent capture in the existing helper. Cover weekday/overnight and DST gaps/folds, duplicate suppression, concurrent jobs, foreground independence, storage limits/folder failures, failed writes and restart/suspend recovery. Confirm no active child survives final plugin shutdown. Test against real local-stream processes as well as fakes.
3. **Native UI and lifecycle:** add schedule editor, library playback/deletion, recording folder/cap settings and diagnostics. Test keyboard/focus, stale edits, file versus live controls and overlapping captures. Verify popup closure/foreground Stop preserve recordings, last-widget disable/removal stops them, and reinstalls preserve schedules/history/files. Report manual suspend and full shell-restart validation separately.

## Remaining discussion

- Confirm the recommended mono 32 kbit/s Opus profile after a listening/capture test, and the FFmpeg dependency.
- Set final defaults for storage cap, free-space reserve and concurrent jobs. Proposed starting values are 5 GiB, 1 GiB and 3 jobs, respectively.
- Confirm manual deletion when full as the default; automatic oldest-first cleanup could be a later explicit option.
- Retain the proposed timezone/DST and partial/missed semantics unless the user chooses different behavior. Disabling/deleting a schedule leaves its active recording running while the plugin remains available, with a separate Stop recording action; saved files remain until deleted.
